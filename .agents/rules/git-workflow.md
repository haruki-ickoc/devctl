# Git 運用およびコミット規約 (git-workflow.md)

このリポジトリにおける Git ブランチの運用、コミットメッセージの作成、およびプルリクエスト（PR）の起票ルールを定めます。エージェントは変更をコミットまたは PR 作成する際、本規約に厳格に従ってください。

---

## 1. ブランチ運用モデル

原則として `develop` ブランチを起点・マージ先とするブランチ運用を行います。

- **`main`**: リリース済み安定版ブランチ。直接のコミットは行いません。
- **`develop`**: 開発統合ブランチ。すべての機能追加・改修はここから分岐し、PR 経由でマージされます。
- **`feature/<機能名>`**: 新機能の追加、仕様変更、改善作業用ブランチ（例: `feature/build-command`, `feature/agent-rules-and-skills`）。
- **`fix/<課題名>`**: バグ修正用ブランチ（例: `fix/subnet-detection-error`）。
- **`release/<バージョン>`**: リリース確定・タグ打ち準備ブランチ（例: `release/1.1.0`）。

### ブランチ作業の原則
1. 作業開始時は必ず最新の `develop` から `feature/*` または `fix/*` ブランチをチェックアウトすること。
2. 他の作業内容を1つのブランチに混在させず、計画書（`releasenote/v<バージョン>-plan.md`）の単位でブランチを分離すること。

## 2. コミットメッセージ規約

コミットメッセージは**原則「日本語」**で記述してください。変更内容の意図が第三者やレビュアーに即座に伝わるよう、以下の書式を順守します。

### 基本フォーマット

```text
<prefix>: <簡潔な変更概要> (v<対象バージョン>)

- <変更した主要ポイント1>
- <変更した主要ポイント2>
- <関連したドキュメントやテストの更新内容>
- closes #<Issue番号>（該当する場合）
```

### プレフィックス (`<prefix>`) の分類
| プレフィックス | 用途 |
| :--- | :--- |
| `feat:` | 新機能の追加、新しいサブコマンドやフラグの追加 |
| `fix:` | バグ修正、予期せぬ動作の是正 |
| `docs:` | ドキュメント、README、リリースノート、アイデア草案のみの変更 |
| `refactor:` | 挙動を変えないコードのリファクタリング・責務整理 |
| `test:` | テストコードの追加・修正 |
| `chore:` | エージェント規約、ビルド設定、依存関係などの雑務更新 |

### 記述例

```text
feat: コンテナイメージのビルド専用コマンド (build) の追加 (v1.1.0)

- internal/docker/compose.go に Build メソッドを追加し、--dry-run 対応と失敗伝播を担保
- devctl project build およびトップレベル短縮コマンド devctl build を新設
- 特定サービス（services...）の個別指定およびカレントディレクトリからのプロジェクト自動検出に対応
- --no-cache, --pull, -f / --file フラグをサポート
- internal/docker/compose_test.go および internal/cmd/project_test.go に単体テストを追加
- README.md および configs/config.example.yaml に build コマンドの使用法とガイダンスを追記
- v1.1.0 の計画書およびリリースノート (v1.1.0-plan.md, v1.1.0-released.md) を追加
- closes #3
```

## 3. プルリクエスト（PR）規約

1. **言語の統一**:
   - タイトル・本文ともに**原則「日本語」**で記載すること。
2. **マージ先の指定**:
   - 通常の開発 PR の Base ブランチは必ず `develop` を指定すること（直接 `main` へ向けない）。
3. **PR 本文の記載項目**:
   - `.agents/skills/create-pr/resources/pr-template.md` に基づき、以下の要素を必ず含めること：
     - **概要**: 変更の目的・解決する課題
     - **主な変更点**: パッケージ・ファイルごとの変更内容
     - **関連 Issue**: `Closes #XX` 等の Issue リンク
     - **破壊的変更の有無**: 後方互換性への影響
     - **動作確認・検証結果**: `verify.sh` のログや実行確認結果

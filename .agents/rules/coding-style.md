# コーディング規約と設計方針 (coding-style.md)

このリポジトリのコードを変更・追加する際は、以下の規約と設計原則を厳格に順守してください。

## 1. パッケージ構成と責務の分離 (Standard Go Layout)

- `cmd/devctl/`: CLIのエントリポイントのみを配置します。フラグ処理やビジネスロジックは記述せず、`internal/cmd` のルートコマンド呼び出しのみにとどめてください。
- `internal/cmd/`: Cobraコマンド群を配置します。入力引数の検証、フラグの受け渡し、他パッケージのオーケストレーションのみを担当し、重い処理ロジックは直接実装しないでください。
- `internal/config/`: 設定ファイル（YAML）のロード、バリデーション、チルダ展開、環境変数展開を担当します。他の内部ロジックに依存しない独立した設計を維持してください。
- `internal/docker/`: Docker CLIおよびDocker Composeのコマンド構築と実行を担当します。外部コマンド呼び出しはこのパッケージ内に限定してください。
- `internal/ui/`: 端末出力の装飾（カラー表示、アイコン、メッセージ書式）を担当します。出力フォーマットの一貫性を保つため、標準の `fmt.Println` を各所に散乱させず、極力このパッケージのユーティリティを使用してください。

## 2. コマンド実装とフラグ規約

- すべてのサブコマンドで、グローバルフラグ（`--config`, `--dry-run`, `--verbose`）が正常に機能する設計にしてください。
- エイリアスや短縮コマンド（例: `project up` に対する `up`）を定義する場合は、既存のコマンド体系と衝突しないことを確認してください。

## 3. 外部実行（Docker/OS）の制約

- コマンド実行には直接 `os/exec` を個別実装せず、必ず `internal/docker/runner.go` 等の抽象化層を経由してください。
- `--dry-run` フラグが指定された場合は、外部コマンドを実行せず、実行予定のコマンド文字列を正確にログ出力してください。

## 4. エラーハンドリングとロギング

- エラーは握りつぶさず、呼び出し元へ適切に返却（ラップ）してください。
- ユーザー向けの致命的なエラーメッセージには、原因だけでなく可能な限り「解決策」や「確認すべきコマンド」を提示してください。
- 異常終了時は適切な終了コード（非ゼロ）を返してください。

## 5. コード整形と品質基準

- すべてのコードは `go fmt` に準拠したフォーマットを適用してください。
- コミット前に `go vet ./...` を実行し、静的解析警告が0件であることを確認してください。
- CGOは使用せず、`CGO_ENABLED=0` で静的リンクされた単一バイナリが生成できる実装を維持してください。
